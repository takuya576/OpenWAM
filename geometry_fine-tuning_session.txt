● I'd use GAE as a frozen geometry teacher during training, not as a replacement
  for OpenWAM's latent space. The plan: precompute GAE latents for every YAM
  frame offline, then add a training-only loss that makes the Wan DiT's video
  tokens predict them. This adds nothing at deploy time and keeps the checkpoint
  format. Feeding geometry in as an extra input is a stronger but costlier
  second step, because it needs DA3-Giant running in the policy loop.

  What shapes the design

  - Token grid is the boundary bottleneck. The DiT sees the 384×320 (H×W) canvas
    at 32×32 px per token. That is 12×10 tokens per latent frame and 3 latent
    frames, where frame 0 is the clean current observation. The head camera gets
    8×10 tokens and each wrist camera 4×5. So geometry has to be supervised
    below token resolution, or it won't sharpen boundaries.
  - The action expert reads video tokens at all 30 layers through joint
    attention. Geometry-aware video tokens therefore reach the action without
    changing the action expert.
  - GAE's latent is more than depth. It has 64 channels per 14-px patch, can be
    decoded to depth and rays by the frozen DA3 head, and is aligned to
    C-RADIO/DINOv2 features. So it also captures which pixels belong to the same
    object. That matters where the depth edge is weak, like a cube sitting on a
    table.
  - Ruled out:
    - Replacing the Wan VAE with GAE through OpenWAM's external-encoder path
      needs from_scratch=true, which throws away the foundation DiT. That isn't
      viable with about 50 demos.
    - GAE's flow model generates whole scenes from camera paths, so it doesn't
      apply here; only the codec is useful.
  - Deploy loads checkpoints strictly (base.py:679
    (openwam/model/architectures/base.py#L679)). Training-only modules must be
    stripped at save time, the way LoRA keys are in checkpointing.py:195
    (openwam/train/utils/checkpointing.py#L195).
  - Separate environments. GAE runs in the gae env (torch 2.5.1) and OpenWAM in
    openwam (torch 2.7.1). An offline cache keeps them apart for training.

  1. Does GAE work on robot views? Run GAE reconstruction on YAM head and wrist
     frames from all three tasks. Compare GAE-decoded depth with raw DA3 depth
     at the cube, ring, peg and bottle edges. Also compare single-frame encoding

     64-channel bottleneck blurs the ring or peg, use DA3 depth or PCA-reduced

  2. Measure the baseline's boundary sensitivity. Freeze your best LoRA
     checkpoint. Train a linear probe from frame-0 tokens at layers {5, 10, 15,
     20, 25} to a depth-edge map, and report edge F1 on held-out episodes. That
     gives a number to beat and shows which layers lack geometry.

  Phase 1: offline geometry cache

  - Build script (in the gae env):
    - Resize each 480×640 frame to 378×504 (27×36 patches) and run DA3-Giant
      plus the codec encoder.
    - Standardize the result with latent_stats_gae_64.pt.
    - Resample each camera into its canvas slot at 16 px, stretched the same way
      the RGB is. Each frame becomes 64×24×20, exactly the Wan VAE latent grid.
    - Also store a depth-edge map and an object-edge map (cosine distance
      between neighbouring GAE cells) at the same grid.
  - Size: about 60 KB per frame in fp16, roughly 1 GB per task. Reserve the disk
    space first.
  - Dataloader: return the maps for the same frame indices as the video and mask
    padded frames. Targets come from frames without colour jitter, so
    ColorJitter stays as it is.

  Phase 2: geometry alignment loss (main experiment)

  This is the same idea as Geometry Forcing (for video diffusion models) and
  Spatial Forcing (for VLAs), both of which aligned to VGGT features; here the
  target is GAE.
  - Hidden states: capture video-token hidden states at one layer ℓ inside the
    joint loop (mot_driver.py:306
    (openwam/model/architectures/dual_system/mot_driver.py#L306)).
  - Projector: an MLP 3072 → 2048 → 64 × (2×2 sub-cells) × (frames per latent
    frame: 1 for frame 0, 4 for frames 1–2). The 2×2 sub-cell output is what
    makes each 32-px token encode where a boundary crosses it.
  - Loss terms:
    - Per-cell cosine plus a small L2 term. The L2 keeps predictions decodable
      through GAE and the DPT head, so you can view the depth the model sees and
      imagines.
    - A relation loss that matches cell-to-cell similarity within each camera.
      This is GAE's own structure loss and directly encodes "same object or
      not".
    - Cells weighted by 1 + β·edge.
    - Future frames weighted by (1−σ), because geometry at high noise is a
      guess.
  - Projector handling: it trains as part of the architecture but is stripped
    from the saved checkpoint, so deploy and open-loop eval are unchanged. It is
    saved separately for diagnostics.
  - Arms on place_cube_right n56 delta LoRA (baseline best held-out MAE is
    0.0509 at step 3072):
    - G1: frame 0 only, ℓ=10, λ=0.5.
    - G2: all frames plus the relation loss, ℓ=10, λ=0.5.
    - G3: G2 with ℓ=20.
    - G4: G2 plus edge weighting on both the alignment loss and the video
      flow-matching loss.
    - Baseline, second seed: to know the noise floor.
  - Cost: about 5 runs × 3–4 h on 4×L40S.
  - Follow-up: run the winner on hang_ring next (thin ring and peg, the task
    most limited by boundaries), then on stand_up_bottle.

  Phase 3: explicit geometry input (only if Phase 2 isn't enough)

  - Adapter: a zero-init Conv(64→3072, kernel 2, stride 2) on the frame-0 GAE
    map, added to the frame-0 tokens right after patchify (wan_backbone.py:421
    (openwam/model/video_backbone/wan_backbone.py#L421)). This mirrors Wan's
    existing control_adapter hook.
  - Geometry dropout: about 0.15, so the RGB path stays strong.
  - Deploy:
    - DA3-Giant plus the codec encoder run on the 3 live images every chunk. My
      rough estimate is about 6–7 TFLOP, on the order of 0.1 s on an L40S-class
      GPU; this needs measuring.
    - The GAE code has to run next to the server. Either install its
      dependencies in the openwam env (the torch 2.7.1 vs 2.5.1 difference must
      be checked) or run it as a side process in the gae env.
    - The adapter is saved in the checkpoint and built from config at deploy.
  - If this helps: the next step is to add GAE channels as zero-init extra
    input/output channels of patch_embedding and head. Your LoRA recipe already
    trains both in full. The model would then predict future geometry together
    with RGB.

  Evaluation

  - Primary offline metric: held-out open-loop MAE at each arm's best
    checkpoint, not training loss. Split it by phase (approach, contact,
    transport) using gripper events; geometry should help most near contact.
  - Boundary metrics: the Phase 0 probe F1, plus DA3 run on generated vs
    recorded frames in open_loop_eval (depth AbsRel and depth-edge F1).
  - Real robot: at least 20 trials per arm per task, on a fixed list of object
    placements, alternating arms. Record why each failure happened, e.g.
    misjudged edge vs. something else. Twenty trials only show large
    differences, roughly 50% → 80%.
  - Adoption rule: better held-out MAE on at least 2 of 3 tasks, and no worse on
    the robot.

  Risks

  - Domain gap: GAE was trained on scene videos, not close-range wrist views.
    Phase 0 decides whether it transfers.
  - Resolution ceiling: the 32-px token limits boundary precision. If Phase 2
    helps but plateaus, a larger canvas is the next step, but it is expensive
    because it changes the foundation model's training resolution.
  - Small data: with about 50 episodes the extra loss also acts as a regularizer
    and may slow action-loss fitting. Watch both curves; the λ values in the
    sweep cover this.
  - Licensing: DA3-Giant is CC BY-NC 4.0 and GAE has its own Tencent license.
    That's fine for research; check before any commercial use.
